# ADR-0007 - IDs de fonte = id do catálogo; aliases; fallback SerpAPI = googleplay

- Status: aceita
- Data: 2026-08-30
- Escopo: datareview_v4

## Contexto

O legado v1 usava vários identificadores para a mesma fonte (id interno,
nome de rota, label de UI e o id correto da fonte). Nas rotas `/api/run` e na
página Fontes, o usuário referencia a fonte por `source`. A ambiguidade já virou
bug no passado (ex.: a fonte "Google" do Suggest vs o produto SerpAPI "Google").

## Decisão

- **O id da fonte (rota, adaptador, persistência) É o id do catálogo**
  (`packages/sources/src/catalog/`). Nada de ids próprios em paralelo.
- **Aliases no catálogo** absorvem nomes consagrados do legado sem conflito
  com um id real: `apple-podcasts` → `apple`, `coingecko` → `kraken`/cotas,
  `open-meteo`
  → `wttr.in`/clima, `brasil` → grupo de fontes BR, `google` → `suggest`/serp.
- **O fallback SerpAPI é registrado como `googleplay`** (não `google`): o id
  `google` fica reservado à família Google Search/Suggest, e `googleplay` é o
  produto SerpAPI exato (Play Store) quando a fonte primária da loja falha.
  `engine` e `country` são parâmetros de rota, nunca fonte.

## Consequências

Positivas: um id por fonte em todo o sistema; `/api/catalog` expõe `aliases` e
os testes de rota garantem que aliase resolve para o mesmo catálogo. Riscos:
usar `source: google` com o produto de loja esperado quebra — a UI/Fontes já
expõe claramente o id real e o alias.

- `apps/api/src/routes.ts` (resolução fonte → adaptador)
- `apps/api/test/api.test.ts` (testes de alias + erro honesto)
